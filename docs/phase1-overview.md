## 1. 项目定位与设计哲学

### 1.1 CodeBot 是什么？

CodeBot 是一个**终端 AI 编程助手**。你把它想象成终端里的 AI 程序员——你告诉它"帮我修复这个 bug"或者"给这个模块写单元测试"，它会自己：

- 读文件理解代码
- 搜索相关代码片段
- 编辑文件
- 运行命令验证
- 在循环中迭代直到完成

和 GitHub Copilot（写一行补一行）不同，CodeBot 是**自主 Agent**——它自己决定要做什么、调用什么工具、什么时候算完成。

### 1.2 四大设计原则

**原则一：两种工作模式，应对不同风险**

- **日常模式（ReAct）**：直接开工，边想边做。说"修复 bug"就直接读文件、改代码、跑测试。
- **Plan 模式**：高风险任务先规划。Agent 先探索代码、写出详细计划，你审核通过后才开始动手。在 Plan 模式中，Agent 只能读代码和写计划文件，其他写操作全被拦截。

**原则二：分层架构，职责清晰**

交互层 → 引擎层 → 工具层 → 记忆层 → 安全层。每层只管自己的事，通过明确接口通信。这就像工厂流水线，每个工位只做一件事。

**原则三：厂商中立，不绑定模型**

同时支持 Anthropic（Claude）、OpenAI（GPT）、DeepSeek 以及任何兼容 OpenAI API 的服务。Agent 核心代码完全不知道底层用的是哪个模型——通过统一接口屏蔽差异。

**原则四：安全优先**

默认情况下，读文件自动放行，写文件和执行命令需要你确认。安全层有 5 道防线（白名单→黑名单→沙箱→自定义规则→模式控制），任一道防线拦截就能阻止危险操作。

## 2. 五层分层架构

### 2.1 架构全景图

把 CodeBot 想象成五层楼的建筑，从上到下每层各司其职：

```
┌──────────────────────────────────────────────────┐
│  1F 交互层 (TUI)   你看到和操作的终端界面            │
│  负责：显示消息、接收输入、弹出确认框                 │
│  比如：你输入"修复bug" → 这一层把文字送下去            │
├──────────────────────────────────────────────────┤
│  2F 引擎层 (Agent)  大脑——决定做什么、怎么做          │
│  负责：循环思考→行动→观察，直到任务完成                │
│  比如：收到"修复bug"后，决定"先读文件理解代码"          │
├──────────────────────────────────────────────────┤
│  3F 工具层 (Tools)  手脚——真正干活的地方              │
│  负责：读文件、写文件、搜代码、跑命令、派发子Agent      │
│  比如：引擎层说"读main.py"，这一层去读并返回内容        │
├──────────────────────────────────────────────────┤
│  4F 记忆层 (Memory) 记事本——跨对话记住信息            │
│  负责：记录用户偏好、项目知识，对话太长时压缩            │
│  比如：你上次说"不要用class"，下次对话Agent还记得       │
├──────────────────────────────────────────────────┤
│  5F 安全层 (Security) 门禁系统——防止Agent搞破坏        │
│  负责：检查每个操作是否安全，拦截危险命令                │
│  比如：Agent想执行rm -rf /→ 5道防线全部拦截            │
└──────────────────────────────────────────────────┘
```

### 2.2 一次请求的完整旅程

你说"帮我分析这段代码的问题"，这一路上发生了什么：

1. **交互层**收到你的输入，展开 `@文件名` 引用，识别 `/命令`
2. **引擎层**的 Agent 拿到消息，先注入环境信息（"你当前在哪个目录"）和长期记忆（"用户偏好简洁代码"）
3. Agent 开始**思考**：调用 LLM，LLM 返回"我应该先读取文件"
4. Agent 准备**行动**：调用 ReadFile 工具
5. **安全层**检查：读文件 → 只读操作 → 安全 → 放行
6. 文件内容返回，Agent **观察**结果："代码里有个死循环"
7. Agent 再次**思考**：调用 LLM，"第42行的 while True 没有退出条件"
8. Agent **行动**：调用 EditFile 修复
9. **安全层**再次检查：写文件 → 需要确认 → 弹窗问你"允许吗？"
10. 你点允许，修改完成。Agent 继续循环直到认为任务完成。

这就是 ReAct（推理+行动）循环的核心——Think → Act → Observe → Loop。

### 2.3 为什么是五层？

这分层不是拍脑袋决定的，而是参考了业界顶级方案（Anthropic 的 Claude Code、OpenAI 的 Codex CLI）的实践：

| 层次 | 解决的问题 | 如果不分层 |
|------|---------|----------|
| 交互层 | 用户怎么舒服地使用？ | UI 代码散落在业务逻辑里，想换个界面就得重写整个项目 |
| 引擎层 | LLM 怎么自主完成任务？ | 核心循环和 UI、工具逻辑混在一起，改一点牵动全身 |
| 工具层 | 怎么给 Agent 扩展能力？ | 加一个工具要改十几处代码，还容易引入 bug |
| 记忆层 | Agent 怎么记住跨对话的信息？ | 每次开新对话都是"失忆"状态，用户体验极差 |
| 安全层 | 怎么防止 AI 误操作？ | 安全检查东一处西一处，总有漏洞 |

## 3. 配置系统

### 3.1 三个配置文件的优先级

CodeBot 启动时按顺序读三个文件，**后读的覆盖先读的**：

1. **`~/.codebot/config.yaml`**（你家目录下）——全局默认值，影响你所有项目
2. **`项目/.codebot/config.yaml`**（项目目录下）——项目级配置，团队共享，提交到 Git
3. **`项目/.codebot/config.local.yaml`**（项目目录下）——你的私人配置，被 .gitignore 忽略

**举例**：团队项目配置用 DeepSeek，但你想本地测试用 Ollama，只需在 `config.local.yaml` 里写你的 Ollama 配置，它会覆盖项目级配置——完全不影响其他人。

### 3.2 不同配置项的合并规则

合并不是简单的"后面全盖前面"，不同项有不同策略：

| 配置项 | 合并方式 | 为什么 |
|--------|---------|--------|
| LLM 提供商 (providers) | **全部覆盖** | 要么用团队的模型，要么用自己的，不能"混用" |
| 权限模式 (permission_mode) | **条件覆盖**：设了非 default 才覆盖 | 团队配了 plan 模式，你用 default 不会被覆盖 |
| MCP 外部工具 (mcp_servers) | **按名称合并**：同名覆盖，不同名追加 | 允许团队加一个、你自己再加一个 |
| 钩子 (hooks) | **全部追加** | 每层的钩子都有价值，不应被覆盖 |
| 开关类 (enable_fork 等) | **或运算**：任一层设为 true 就生效 | 开关类的，更宽松的策略更合理 |

### 3.3 API Key 的智能解析

配置里写 `api_key: ${ANTHROPIC_API_KEY}`，CodeBot 会自动去环境变量里找 `ANTHROPIC_API_KEY` 的值。不写也行——每种协议有默认的环境变量名：

- `anthropic` 协议 → 找 `ANTHROPIC_API_KEY`
- `openai` / `openai-compat` 协议 → 找 `OPENAI_API_KEY`

所以你的 DeepSeek 配置不需要写 api_key，只要设了环境变量 `OPENAI_API_KEY=你的DeepSeek密钥`，系统就会自动读取。

### 3.4 Context Window 的四层自动检测

Context Window（上下文窗口）决定 LLM 能"一次看到多少字"。知道这个值很重要——超了就触发压缩。CodeBot 用四层 fallback 来获取：

- **第一层**：你在配置里写了 `context_window: 128000` → 直接用
- **第二层**：没写？系统自动去 API 端点查询（`GET /v1/models/模型名`），拿到精确值
- **第三层**：API 查询失败？查内置映射表（代码里维护了常见模型的窗口大小）
- **第四层**：映射表也匹配不到？给保守默认值：模型名含 "claude" → 20万，其他 → 12.8万

这保证**永远能拿到一个值**，虽然最后一层可能不准，但宁可低估（提前触发压缩）也不能高估（按超了才报错）。

## 4. 启动流程详解

### 4.1 你在终端敲下 `codebot` 后发生了什么？

整个启动可以分成两段：**准备阶段**（离用户输入还远）和**组装阶段**（把所有零件拼成能用的 Agent）。

**准备阶段**（`main()` 函数）：

1. 创建 `.codebot/` 目录、初始化日志文件
2. 解析命令行参数（比如 `--mode plan` 强制启动 Plan 模式）
3. 加载三份配置文件并合并成一个 `AppConfig`
4. 如果有 Hook 配置，创建 Hook 引擎

**分支**：
- 如果你用了 `-p "分析代码"` → 非交互模式：直接执行任务，打完收工
- 如果只是 `codebot` → 交互模式：启动 TUI，进入组装阶段

**组装阶段**（`CodeBotApp.on_mount()`）：

```
CodeBotApp.on_mount()
  │
  ├── 1. 读取 CODEBOT.md → 获取项目专属指令
  ├── 2. 加载 Skills → 找到所有可用技能包
  ├── 3. 加载 Agent 定义 → 找到 explore/plan/verification 等子Agent定义
  ├── 4. 创建 LLM 客户端 → 根据配置选 Anthropic/OpenAI/OpenAICompat
  ├── 5. 创建工具注册表 → 注册所有内置工具（ReadFile/Bash/Grep...）
  ├── 6. 创建权限检查器 → 五道安全防线
  ├── 7. 创建 Agent 实例 → 把上面的零件组装在一起
  ├── 8. 启动 MCP 连接 → 连上外部工具服务器
  ├── 9. 启动 Worktree 清理任务 → 每小时检查一次过期的工作树
  └── 10. 恢复上次会话（如果有的话）
```

**把第 4~7 步想象成组装一辆车**：LLM 客户端是发动机，工具注册表是轮胎和方向盘，权限检查器是刹车，Agent 实例就是把它们装在一起的底盘。

## 5. 项目目录结构

### 五个核心文件（🔥标记为必看）

| 文件 | 作用 | 行数 |
|------|------|------|
| `agent.py` | **Agent 主循环**——ReAct 循环、Plan 模式、max_tokens 恢复 | ~1300 |
| `app.py` | **TUI 应用**——终端界面的全部逻辑 | ~1900 |
| `client.py` | **LLM 客户端**——Anthropic/OpenAI/DeepSeek三合一适配器 | ~800 |
| `tools/base.py` | **工具基类**——所有工具的模板 | ~80 |
| `permissions/checker.py` | **权限检查器**——五层安全检查的核心 | ~120 |

### 目录结构口诀

记住这个口诀：

> **app 管界面，agent 管循环，client 管模型，tools 管能力，permissions 管安全，memory 管记忆，context 管窗口**

每个目录都是一个独立子系统：

- `tools/` — Agent 的"手脚"（读文件、写文件、跑命令、搜代码...共20多个工具）
- `agents/` — 子Agent 系统（可以派发子任务给 explore/plan/verification Agent）
- `teams/` — 多Agent 团队协作（Coordinator 分配任务给多个 Worker）
- `skills/` — 技能包（commit/review/test 等 SOP，改变 Agent 的行为模式）
- `commands/` — 斜杠命令（/clear /compact /status /review 等14个命令）
- `hooks/` — 生命周期钩子（在 Agent 执行各阶段自动触发自定义脚本）
- `mcp/` — MCP 协议支持（接入外部工具服务，如 GitHub、数据库）
- `worktree/` — Git Worktree 隔离（在独立分支上工作，不影响主分支）
- `context/` — 上下文管理（自动压缩长对话，防止超出 token 限制）
- `memory/` — 记忆系统（跨对话记住用户偏好和项目知识）

## 6. 技术栈全景图

| 技术 | 做什么 | 选它的原因 |
|------|------|----------|
| **Textual** | 终端 UI 框架 | 支持 CSS 样式、响应式布局、组件化——能做复杂终端应用 |
| **Anthropic SDK** | 调 Claude 模型 | 官方 SDK，Prompt Caching 节省费用，Extended Thinking |
| **OpenAI SDK** | 调 GPT 和 DeepSeek | 官方 SDK，生态最大，兼容服务最多 |
| **Pydantic v2** | 数据校验 + Schema 生成 | 自动生成 JSON Schema（LLM function calling 刚需） |
| **mcp** | 外部工具扩展 | 标准化协议，任何语言实现的 MCP Server 都能接入 |
| **PyYAML** | 读配置文件 | Python 生态标配 |
| **HTTPX** | HTTP 客户端 | 支持异步，用于 MCP SSE 连接 |
| **uv** | 包管理 | Rust 实现，比 pip 快 10-100 倍 |
| **pytest** | 测试 | Python 测试标准 |

### 一个关键决策：为什么直接用两个 SDK 而不是用 litellm 这样的统一层？

因为 Anthropic 有 Prompt Caching 和 Extended Thinking 这些独有功能，用统一抽象层要么放弃这些功能，要么做一堆补丁。直接集成两个官方 SDK，**自己实现抽象层**，既享受最新特性，又不被供应商锁定。

## 7. 关键设计模式

### 7.1 策略模式 — 切换模型不换代码

你想从 DeepSeek 换到 Claude，只改一行配置。这就是策略模式的威力：

- **抽象策略**：`LLMClient` 接口（只要求实现一个 `stream()` 方法）
- **具体策略**：Anthropic 客户端、OpenAI 客户端、OpenAI 兼容客户端
- **工厂函数**：读取配置中的 protocol 字段，自动选对应的客户端

Agent 代码里只调用 `client.stream()`，完全不知道底层是哪个模型。

### 7.2 管道模式 — 五道安全检查逐个过关

每个工具调用都要走一条"管道"，经过五道关卡：

```
工具调用 → [是安全命令吗？] → [是危险命令吗？] → [在允许的目录内吗？]
               → [用户有自定义规则吗？] → [当前模式放行吗？] → 决定
```

每道关卡返回"允许"、"拒绝"或"问用户"。任一关说"拒绝"就立即终止——就像机场安检，有一项不合格就过不去。

### 7.3 观察者模式 — Hook 自动响应

Agent 在七个关键时刻（会话开始/结束、每轮开始/结束、工具执行前后、LLM 调用前后）广播通知，你配置的 Hook 收到通知后自动执行。这就像 Git Hook——每次 commit 前自动跑 lint。

### 7.4 异步生成器模式 — 流式输出

Agent 不是一次性返回结果的——它用 `yield` 把事件逐个推送给 TUI：
- yield 一个字 → TUI 显示一个字（打字机效果）
- yield 一个工具调用 → TUI 显示工具卡片
- yield 一个权限请求 → TUI 弹确认框

这就像视频流——服务端边生成边推，客户端边收边播。

### 7.5 注册表模式 — 所有东西都是"注册-查找"

工具、技能、子Agent、命令——全部用注册表管理。想加一个新工具？
1. 继承 `Tool` 基类
2. 实现 `execute()` 方法
3. 调 `registry.register(your_tool)`

不需要改任何核心代码。所有可扩展系统都是这个套路。
