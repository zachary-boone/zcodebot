## 1. 对话管理器：Agent 的短期记忆

### 1.1 对话历史就是一条"消息列表"

Agent 说的每句话、执行的每个工具，都记录在一个消息列表里：

```
[0] 用户: 帮我分析代码
[1] 系统: 当前工作目录是 /project/src
[2] 系统提醒: 用户偏好简洁代码
[3] 助手: 我来读取 main.py → [ReadFile tool_call]
[4] 系统: ReadFile 结果: import os...
[5] 助手: 代码中第 42 行有问题 → [EditFile tool_call]
[6] 系统: EditFile 结果: 修改成功
[7] 助手: 修好了，第 42 行的死循环已修复
```

### 1.2 为什么所有东西都伪装成"用户消息"？

Anthropic 的 Messages API 要求消息的 role 严格交替：user → assistant → user → assistant...。工具执行结果和系统提醒的 role 也是 user——因为它们的本质都是"给 LLM 提供新信息"，归入 user 侧最自然。

系统提醒（Plan 模式提示、延迟工具列表）会用 XML 标签 `<system-reminder>` 包裹，和普通用户输入区分开。

### 1.3 三个特殊注入

- **环境上下文**：插在 history[0] 位置（LLM 最先看到），内容如"你运行在 Windows 上，当前目录是 /project/src"
- **长期记忆**：插在 history[0] 或 history[1] 位置，内容是 memories.md 的内容
- **系统提醒**：追加在 history 末尾（最近一条），内容是当前轮次的临时提示

### 1.4 消息中包含了什么

一条消息不是简单的"字符串"。它可能包含：
- 文本内容（LLM 说的话）
- 工具调用列表（LLM 要执行什么工具）
- 工具结果列表（工具返回了什么）
- 思考块（LLM 的内部思考过程）

## 2. Token 估算：不做精确计算也能用

### 2.1 问题

每次 LLM API 调用后才返回精确的 token 用量。但在两次调用之间，我们追加了工具结果和系统提醒——这些新消息的 token 数未知。

如果不知道当前总 token 数，就不知道什么时候该触发压缩。

### 2.2 混合估算策略

**核心思路**：精确值 + 估算值 = 足够用的近似值。

- **精确部分**：最近一次 LLM API 返回的 token 用量（作为"锚点"）
- **估算部分**：锚点之后追加的消息，用简单公式估算（总字符数 ÷ 3.5 ≈ token 数）

**为什么是 3.5？** 经验值。英文约 4 字符/token，中文约 1-2 字符/token，混着用取 3.5 是个实用的折中。**这个估算只用于"锚点后的增量"**，最坏情况也就差几个百分点，够用。

### 2.3 锚定时机

每次 LLM 返回后，立刻"钉下锚点"：记录当前消息列表的长度和精确 token 数。下次估算时只算新增的消息。

如果对话被压缩（历史被替换），锚点失效，退化为全字符估算——但压缩后的对话通常很短，全字符估算也差不了多少。

## 3. 双层压缩策略

当对话太长（接近 context window 上限），必须压缩。CodeBot 用了两层：

### Layer 1：工具结果裁剪（每次 LLM 调用前）

**问题**：一次工具调用可能返回巨大的输出（10MB 日志文件）。太多大结果会快速塞满上下文。

**解法**：两个阈值：
- 单条结果超过 5 万字符 → 截断
- 本轮所有结果合计超过 20 万字符 → 最早的几条替换为"结果已保存在磁盘，路径是 xxx"

**关键设计**：截断只作用于发送给 LLM 的副本（api_conv），原始对话（conversation）保持完整，用于持久化。

### Layer 2：自动对话压缩（token 快超时才触发）

**触发条件**：估算的 token 数 ≥ context_window - 13K（给输出留安全边距）

**压缩算法分三步**：

**第一步：分割**
把消息列表从后往前切成两段：
- **prefix（前缀）**：老消息，需要被压缩成摘要
- **keep（尾部）**：最近的消息，保留原文

保留的尾部约 10K tokens（通常 5-15 条消息），因为最近几轮对话的细节对后续推理至关重要。

**第二步：生成摘要**
调用 LLM，用特定的 9 段结构 Prompt（请求意图、关键技术、文件代码、错误修复、用户消息原文、待办、当前工作、下一步）把 prefix 压缩成一个结构化摘要。

**第三步：组装**
把 摘要 + 恢复附件 + 保留的尾部 拼成新的对话历史，替换旧的。

### 3.3 压缩后不丢失上下文：RecoveryState

压缩后 LLM 失去了之前的文件内容。如果它刚读了 5 个文件，压缩后全忘了，就要重读——浪费时间和 token。

**解法**：每次读文件时，把文件内容快照缓存在 RecoveryState 里。压缩时把这些快照作为附件加到摘要后面（标注"这是旧快照，需要最新内容请重新读取"）。LLM 压缩后仍然保有工作上下文。

### 3.4 断路器：防止频繁压缩

如果对话刚好在阈值附近，可能在压缩和继续对话之间反复横跳。断路器在短时间内阻止第二次压缩，给对话足够的"增长空间"。

## 4. 自动记忆提取：跨对话的长期记忆

### 4.1 怎么工作的？

Agent 每完成 5 轮对话，就在后台异步触发一次记忆提取：

1. 把最近对话内容发给 LLM
2. LLM 分析对话，提取有价值的信息，分成四类：
   - **用户偏好**："用户喜欢用 snake_case"
   - **纠正反馈**："上次用户说不准用 type: ignore"
   - **项目知识**："项目用 PostgreSQL 15"
   - **参考资料**："API 文档在 docs.example.com"
3. 和已有记忆合并去重，写入文件

### 4.2 两个存储位置

- `~/.codebot/memories.md` — **用户级**，跨所有项目共享（"用户偏好简洁代码"）
- `项目/.codebot/memories.md` — **项目级**，只在此项目生效（"这个项目用 PostgreSQL 15"）

两个文件的内容在下次新对话开始时一并注入。

### 4.3 关键设计：异步非阻塞

记忆提取不用 `await`，而是用 `asyncio.ensure_future()` 在后台执行。Agent 主循环不等它完成就继续处理下一轮。否则用户每 5 轮就要多等 2-3 秒等待 LLM 生成记忆摘要。

## 5. 会话持久化

### 5.1 存储格式

对话以 JSONL（每行一个 JSON 对象）格式存在 `.codebot/sessions/{session_id}.jsonl`。每条记录有类型标记（用户消息、助手消息、工具结果、压缩边界）。

### 5.2 恢复机制

重新打开 CodeBot 时，可以恢复上次的会话。如果会话经历了压缩，就恢复压缩后的状态（摘要 + 尾部），不重放被压缩掉的前缀。

### 5.3 会话摘要

每次会话结束时，用 LLM 生成一句话摘要（"用户重构了 auth 模块，将 token 逻辑提取到独立服务"），作为会话列表的标题。

## 6. 面试高频点

### 6.1 "Context Window 有限，怎么管理长对话？"

双层压缩策略：

**Layer 1**：每次 LLM 调用前，裁剪过大的工具结果（单条 > 5 万字符截断，累计 > 20 万替换为文件引用）。

**Layer 2**：当 token 快超时，用 LLM 生成历史对话的结构化摘要，保留近期 1 万 token 原文，替换整个对话历史。

另外通过 RecoveryState 保存最近读取的文件快照，压缩后 LLM 仍保有工作上下文。

### 6.2 "Token 数怎么估算？不调用 tokenizer 能准吗？"

混合策略：API 返回精确值后钉为锚点，锚点之后的消息用字符数 ÷ 3.5 估算。误差仅在锚点后的小增量上，完全够用。不需要额外调 API 也不用引 tokenizer 库。

### 6.3 "跨对话怎么能记住用户偏好？"

自动记忆提取：每 5 轮对话，后台异步让 LLM 分析对话，按四类（偏好、反馈、项目知识、参考资料）提取记忆，写入用户的 ~/.codebot/memories.md 和项目的 .codebot/memories.md。下次新对话启动时注入到开头。

### 6.4 "压缩时为什么保留近期原文？"

全部压缩会丢失精确信息（代码片段、文件路径、错误信息），导致无法继续 EditFile（old_string 必须精确）。保留最近约 1 万 token 的原文确保 LLM 仍有足够的上文进行精确操作。
